01

Зачем нужен Kubernetes

Docker запускает контейнер. Kubernetes управляет контейнерными приложениями на группе машин: размещает их, следит за состоянием и поддерживает нужное число экземпляров.

Ты описываешь желаемое состояние.

«Нужно три копии веб-сервера». Контроллеры сравнивают желаемое состояние с текущим и стараются устранить разницу. Если один Pod исчезнет, контроллер создаст замену.

Docker Compose удобен для приложения на одном хосте. Kubernetes добавляет управление несколькими узлами, обнаружение сервисов и механизмы обновления. За это приходится платить сложностью: для небольшого проекта он нужен далеко не всегда.

02

Как устроен кластер

Control plane

API server принимает запросы; etcd хранит данные кластера. Контроллеры поддерживают желаемое состояние, scheduler выбирает узел для нового Pod.

Worker node

Рабочая машина. kubelet следит за Pod на узле, а container runtime запускает контейнеры. Сетевые компоненты обеспечивают связь.

kubectl — клиент Kubernetes API. Команда kubectl apply отправляет объект в API server; сам kubectl не размещает контейнеры и не выполняет роль scheduler.

03

Pod → ReplicaSet → Deployment

Pod — минимальная единица развёртывания: один или несколько контейнеров с общей сетью и подключёнными томами. Pod может исчезнуть, поэтому приложение обычно запускают через контроллер.

ReplicaSet поддерживает число Pod. Deployment управляет ReplicaSet и обновлениями приложения. Меняя spec.replicas, ты задаёшь желаемое число копий; меняя шаблон Pod — запускаешь обновление.

Удалить Pod ≠ удалить приложение.

Если Pod принадлежит Deployment, его заменят. Чтобы убрать приложение, удали Deployment. Новый Pod получит новое имя и обычно новый IP.

В песочнице ReplicaSet показан как учебная группа NAME-lab. Замена Pod и обновление шаблона происходят сразу: настоящий rolling update с несколькими ReplicaSet здесь не моделируется.

04

Service связывает приложение

Service предоставляет стабильную точку доступа к группе Pod. Его selector выбирает Pod по меткам, например app: web. Готовые Pod становятся доступными конечными точками.

port: 80

Порт самого Service, к которому обращается клиент внутри кластера.

targetPort: 80

Порт приложения в контейнере. Если не указан, используется значение port. Запись containerPort сама по себе не запускает сервер.

ClusterIP обычно доступен внутри кластера. Для внешнего доступа используют, например, LoadBalancer, Ingress или Gateway — в зависимости от окружения. В учебной модели запросы не передаются по сети: схема показывает только выбор Pod по меткам и их готовности.

05

Как читать манифест

YAML описывает API-объект. Отступы определяют вложенность; используй пробелы. Маркер --- разделяет несколько документов в одном файле.

ПолеЗначение
apiVersionВерсия API: apps/v1 для Deployment, v1 для Service.
kindТип объекта.
metadata.nameИмя объекта в его пространстве имён.
specЖелаемая конфигурация объекта.
selector.matchLabelsКакими метками Deployment выбирает свои Pod.
templateШаблон создаваемого Pod, включая метки и контейнеры.

Метки шаблона Pod должны удовлетворять selector Deployment. Selector существующего Deployment неизменяем. Selector Service независим: его можно изменить, но неверные метки оставят сервис без подходящих Pod.

06

Твоя первая лаборатория

Редактор — это виртуальный файл app.yaml. Изменения попадут в кластер только после apply. Команды, схема и задания используют одно состояние.

Симулятор в браузере · не настоящий кластер

Только default, Deployment и ClusterIP Service, один контейнер на Pod. Два worker, по 4 условных слота. Произвольные образы не скачиваются: :missing имитирует ошибку загрузки, :broken — сбой процесса. Остальные образы считаются рабочими. Прочие поля YAML могут храниться, но их поведение не моделируется. Сеть, RBAC, тома, probes и реальное распределение ресурсов отсутствуют. Лимиты: до 20 реплик на Deployment, 20 YAML-документов и 50 КБ на манифест.

    07
    Как искать ошибку
    Начни с kubectl get pods, затем изучи kubectl describe pod ИМЯ и kubectl logs ИМЯ. Не все проблемы решаются перезапуском.
    СостояниеЧто проверять
    PendingСобытия scheduler: ресурсы узлов, ограничения размещения, тома. В модели — занятость 8 слотов.
    ImagePullBackOffИмя и тег образа, доступность registry, права загрузки.
    CrashLoopBackOffЛоги, команду запуска и конфигурацию приложения. Это состояние ожидания контейнера, а не фаза Pod.
    Service без endpointsSelector и метки Pod, готовность контейнеров. Также проверь targetPort и порт слушающего приложения.
    Running ещё не означает «готов принимать трафик».
    В настоящем кластере готовность определяют в том числе readiness probes. Здесь для простоты каждый Running Pod сразу считается готовым, а доступность Service вычисляется по меткам.
    

    08
    Повтори в настоящем кластере
    Скачай YAML и попробуй его в отдельном учебном окружении: kind, minikube или k3s. Установи kubectl, проверь kubectl config current-context и убедись, что выбран учебный кластер. Затем выполни kubectl apply -f app.yaml.
    Продолжи с namespaces, ConfigMap и Secret, requests/limits, probes и постоянными томами. После этого изучай Ingress/Gateway, Helm и доставку приложения через CI/CD.
